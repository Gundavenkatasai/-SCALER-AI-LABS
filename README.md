# PII Redaction Engine

A local, formatting-preserving redaction tool for Indian corporate .docx documents — built as my submission for the Scaler AI Labs challenge.

---

## What it does

You upload a Word document. The backend finds personally identifiable information — emails, phone numbers, company names, addresses, DINs, PANs, Aadhaar numbers, and about a dozen other categories — and replaces them with plausible fake values generated by the Faker library. The document comes back looking identical; tables are intact, fonts haven't shifted, hyperlink text is replaced too. The original file never gets stored.

I built this specifically around the KSH International Limited Red Herring Prospectus (a 200+ page legal filing), which has some genuinely annoying structural problems: hyperlinks that contain PII in their href targets, text split across multiple XML `<w:r>` run elements mid-word, and deeply nested tables. Getting all of that right without destroying the formatting took most of the time.

---

## Stack

- **Backend**: Python 3.12, FastAPI, uvicorn
- **Redaction engine**: python-docx, Faker (seed=42 for audit reproducibility), optional spaCy NER
- **Rate limiting**: slowapi (10 uploads/minute per IP)
- **Frontend**: Vite, vanilla JS/CSS — no frameworks
- **History store**: flat JSON file. No database. Felt like overkill for a single-user local tool.

## Setup

```bash
# Backend
cd scalar
py -m pip install -r requirements.txt
py server.py        # runs on port 8000

# Frontend (in a second terminal)
cd scalar/frontend
npm install
npm run dev         # runs on port 5173
```

Open `http://localhost:5173` in your browser. That's it.

spaCy NER is optional. If you want it:
```bash
py -m pip install spacy
py -m spacy download en_core_web_sm
```
Without it the tool falls back to regex-only mode, which catches everything the evaluation harness tests for.

## API endpoints

| Method | Path | What it does |
|--------|------|-------------|
| `GET` | `/api/health` | Liveness check, returns `{"status": "ok"}` |
| `POST` | `/api/redact` | Upload .docx, get back summary + download_id |
| `GET` | `/api/download/{id}` | Download the redacted file |
| `GET` | `/api/history` | List all past jobs (newest first) |
| `GET` | `/api/history/{job_id}` | Get details for one job |
| `DELETE` | `/api/history/{job_id}` | Delete a history entry and its temp file |
| `GET` | `/api/evaluate` | Run the 75-entity test harness |

The `/api/redact` endpoint is rate-limited to 10 requests/minute per IP.

## History feature

Every successful upload gets logged to `history.json` with the job ID, original filename, timestamp, and the redaction summary (entity count, category breakdown, processing time). The History tab in the UI lists all past jobs. You can re-download a redacted file or delete a history entry from there. Deleting an entry also removes the temp file from disk.

I used a JSON file rather than SQLite because the data is append-mostly, there's no concurrent write pressure in a local single-user tool, and adding a database dependency felt like the wrong call for a one-day scope. If this needed to support multiple users or date-range queries, I'd swap to SQLite with a straightforward three-column table.

## How the redaction actually works

The trickiest part is the run-reconstruction problem. Word documents don't store paragraph text as a flat string — they split it across multiple `<w:r>` XML run elements, sometimes mid-word. A regex match for an email might span three runs. The engine builds a "virtual" flat string by concatenating all run texts, runs the regexes against that, then writes the replacements back by tracking character offsets into the run array. It handles hyperlinks separately because their text lives inside `<w:hyperlink>` elements that `paragraph.runs` completely ignores.

Fake values are deterministic per document session (Faker seed=42). If the same email appears 40 times across the document, it always maps to the same fake address. This keeps the document readable after redaction.

## Evaluation

The engine ships with a 75-entity ground-truth test harness covering all supported PII categories. Run it with:

```bash
py redact_pii.py --evaluate
```

Or hit `GET /api/evaluate`. Current results: 100% precision, recall, and F1 on the harness.

## What I'd improve with more time

- The residential address regex is tuned to Maharashtra/Pune-specific keywords. It would miss addresses from other states. A proper address NER model would handle this better.
- The history file has no size cap. If you process hundreds of documents, it grows indefinitely. A simple `maxlen=500` truncation would fix it.
- Temp files aren't automatically cleaned up on server restart. A startup task that deletes anything older than 24 hours would be sensible.
- The frontend has no loading skeleton for the history list — it just shows nothing until the fetch resolves. Minor, but noticeable.
- Tests. The eval harness covers the detection logic but there are no tests for the API endpoints or the run-reconstruction edge cases. That's the first thing I'd add.

---

## Trade-offs (one-day constraint)

No auth. This is a local tool and auth would be wasted complexity here. If it were deployed as a shared service, that changes completely.

The rate limiter uses in-memory state, so it resets on server restart. slowapi supports Redis backends for persistence — not worth it for a local single-user setup.

The consistency mapper (real PII → fake replacement) is per-request, not cross-request. Two separate uploads of the same document will produce different fake values. This is fine for the current use case.
